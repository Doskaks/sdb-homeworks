### Задание 1. СУБД

### Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать 
правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для
каждой предметной области. 

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему? 
 
1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков.
СУБД должна гарантировать целостность и чёткую структуру данных.

      Ответ: тип СУБД: реляционная (SQL), а именно Microsoft SQL Server, PostgreSQL, Oracle Database.  

1.1.* Хеширование стало занимать длительно время, какое API можно использовать для ускорения работы? 

      Ответ:  
            - использовать встроенные, оптимизированные функции СУБД, например расширение pgcrypto в PostgreSQL;  
            - кэшировать результаты с помощью внешнего кэша, например Redis, для часто используемых, но редко меняющихся данных.


1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к 
маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? 
СУБД должны быть гибкими и быстрыми.

      Ответ:  
            - для лендингов - документо-ориентированная NoSQL или быстрая реляционная (MongoDB, PostgreSQL);  
            - для CRM - реляционная SQL или гибридная (Microsoft SQL Server, PostgreSQL).  

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

      Ответ: да, можно. PostgreSQL с её поддержкой как реляционной модели, так и типа данных JSONB может закрыть обе задачи. 
      Для лендингов данные лидов хранятся в JSONB-документах, а для CRM используются строгие таблицы, это даёт структуру, гибкость и позволяет делать сложные запросы.  

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу 
и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

      Ответ: подойдет СУБД реляционная SQL или графовая, это PostgreSQL и Neo4j.  

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это 
реализовать?

      Ответ: да, можно, использовать ту же PostgreSQL, что и в задачах 1.1 или 1.2, это упрощает инфраструктуру и администрирование.  

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов 
по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать
со связями.

      Ответ: тип СУБД графовая NoSQL, например Neo4j, AWS Neptune или JanusGraph.  

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД 
логистов?

      Ответ: лучше создать отдельную, но связанную систему, например основная база закупок — реляционная (PostgreSQL), 
      а графовая база данных логистики используется как расчетный движок, при создании заявки на доставку данные из 
      реляционной базы данных передаются в графовую для построения маршрута, результат возвращается и сохраняется в основной системе.  

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

      Ответ: можно использовать PostgreSQL как основную и универсальную СУБД для задач 1.1, 1.2, 1.3, что обеспечит целостность,
      снизит операционные расходы, но для высоконагруженной и сложной логистики (1.4) лучше использовать специализированную графовую СУБД Neo4j,
      интегрированную с основной реляционной базой.
