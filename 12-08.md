### Задание 1. Резервное копирование

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

### Решение 1

1. Восстановление за предыдущий день:

   - подходит ежедневное полное резервное копирование (Full Backup), в данном случаи можно использовать схему полный бэкап по воскресеньям + дифференциальные (differential) бэкапы ежедневно для ускорения, восстановление — из одного последнего набора файлов.
  
2. Восстановление за час до поломки:

   - необходима комбинация полных бэкапов с частым (каждый час) бэкапом журналов транзакций (Transaction Log Backup) в режиме полного восстановления БД, что позволит восстановить данные на любой момент времени, последовательно применив журналы к полной копии.

3.* Моментальное переключение при поломке:

   - реализуемо с помощью синхронной репликации данных на резервную базу данных, созданную на основе резервной копии основной базы данных (standby-сервер), при сбое основной БД происходит автоматическое переключение на работающую реплику за секунды.

### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*


### Решение 2

1. Команды резервирования данных:

  - резервирование (pg_dump):
```
# Дамп базы в архивном формате
pg_dump -U postgres -F c -f backup.dump mydb

# Дамп в SQL-файл
pg_dump -U postgres mydb > backup.sql
```


Команды восстановления данных:

   - восстановление (pg_restore): 
```
# Из архивного формата
pg_restore -U postgres -d mydb backup.dump

# Из SQL-файла
psql -U postgres -d mydb -f backup.sql
```

2.* Автоматизация:

   - Cron + bash-скрипт;
   - репликация — для мгновенного переключения на резервную БД.

### Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL. 

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*


### Решение 3

1. Инкрементное резервное копирование в MySQL:

   В MySQL нет встроенной команды для инкрементного бэкапа, инкрементное резервное копирование осуществляется с помощью Percona XtraBackup и mysqlbinlog.

   Percona XtraBackup:

```
# Полный бэкап
xtrabackup --backup --target-dir=/backups/full

# Инкрементный бэкап (на основе полного)
xtrabackup --backup --target-dir=/backups/inc1 \
  --incremental-basedir=/backups/full

# Следующий инкрементный бэкап
xtrabackup --backup --target-dir=/backups/inc2 \
  --incremental-basedir=/backups/inc1
```

   mysqlbinlog:
  
```
# 1. Делаем полный дамп
mysqldump --all-databases --single-transaction --flush-logs \
  --master-data=2 > full_backup.sql

# 2. Копируем бинарные логи (инкрементальные изменения)
# Бинарные логи автоматически создаются после FLUSH LOGS
cp /var/lib/mysql/binlog.* /backups/
```

Примечание: для инкрементного копирования необходима активация бинарного лога log-bin в my.cnf



2.* Преимущества реплики перед обычным бэкапом это высокая доступность и масштабирование, а именно:

   - минимальное время простоя;
   - высокая доступность 24/7;
   - масштабирование чтения;
   - тестирование и аналитика;
   - географическое распределение.
  

   Примечание: реплика не заменяет бэкапы, ошибка на мастере (DROP DATABASE) переходит на все реплики, для полной защиты нужны оба решения.
